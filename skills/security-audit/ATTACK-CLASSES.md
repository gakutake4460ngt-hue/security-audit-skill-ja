# 攻撃クラス

#### 攻撃クラス — Phase 1 に基づいて選び、分割する

アプリケーションの種類に関係する攻撃クラスを選ぶ。すべてのクラスがすべてのコードベースに当てはまるわけではない。以下のリストは出発点である。Phase 1 で見つかったアプリケーション固有のクラスを追加し、大規模なコードベースはサブシステムごとに分割する。作業は、脆弱性の発見、検証、修正、優先順位付けとして組み立てる。検証はソースレビューと範囲を限ったローカルフィクスチャにとどめる。ペイロードチェーンを開発したり、ライブサービスで可用性をテストしたり、共有環境で操作を行ったりしてはならない。

`confirmed` を使うのは、ソースの証拠と範囲を限った検証によって、境界全体と意味のある結果が立証された場合に限る。特定のデプロイ環境、プロバイダー、プラットフォーム、アイデンティティ、ランタイムの事実が得られない場合は `needs_validation` を使い、欠けている事実と、それを解決する安全なオーナー観測またはローカルのチェックを記述する。

> **ネイティブ / バイナリ / カーネルのターゲット** (C/C++/Rust-unsafe、カーネルモジュール、パーサーとデコーダー、FFI、並行ランタイム、バイナリローダー、JIT、ファームウェア): [MEMORY-SAFETY-AND-BINARY.md](MEMORY-SAFETY-AND-BINARY.md) のメモリ安全性、整数/ABI、並行性、バイナリローダー、特権インターフェースのクラスを使う。
>
> **AI / LLM / エージェントのターゲット** (チャットボット、RAG、永続メモリ、ツール呼び出しエージェント、MCP サーバー/クライアント、プロンプト組み立て、モデルが制御するアクション): [AI-AND-LLM.md](AI-AND-LLM.md) のコンテキスト、メモリポイズニング、アクションバインディング、ツールスキーマ、MCP アイデンティティ、出力のクラスを使う。
>
> **HTTP、Web、アイデンティティのターゲット** (一般的な Web アプリ、API、リバースプロキシ、CDN、ゲートウェイ、独自の HTTP パーサー、セッション、CSRF、JWT、OAuth/OIDC、SAML、MFA、パスキー、アカウント復旧/連携、API キー、mTLS): [WEB-PROTOCOL-AND-AUTH.md](WEB-PROTOCOL-AND-AUTH.md) を使う。
>
> **クライアントサイドとブラウザのターゲット** (SPA、ブラウザ拡張機能、埋め込み webview、service worker、ブラウザストレージ、ウィンドウ間メッセージング、CORS、WebSocket、DOM レンダリング): [CLIENT-SIDE.md](CLIENT-SIDE.md) を使う。
>
> **サプライチェーンとリリースのターゲット** (依存関係の解決、生成された入力、CI、リリース/署名/プロモーション、アップデート、プラグイン、拡張機能): [SUPPLY-CHAIN-AND-RELEASE.md](SUPPLY-CHAIN-AND-RELEASE.md) を使う。
>
> **クラウドとデプロイのターゲット** (IAM、Infrastructure as Code、コンテナ/Kubernetes、サービスメッシュ、サーバーレス/エッジ、イングレス、プロバイダーのイベント、ランタイム設定): [CLOUD-AND-DEPLOYMENT.md](CLOUD-AND-DEPLOYMENT.md) を使う。
>
> **プロトコル、RPC、メッセージングのターゲット** (gRPC、GraphQL のトランスポート、Protobuf/Cap'n Proto/Thrift、独自プロトコル、キュー、ブローカー、pub/sub、webhook、ストリーミング RPC): [PROTOCOLS-RPC-AND-MESSAGING.md](PROTOCOLS-RPC-AND-MESSAGING.md) を使う。
>
> **リソース枯渇と可用性のターゲット** (信頼できない処理が、共有の CPU、メモリ、ディスク、接続、ワーカー、キュー、クォータ、運用者負担のコストを消費し得るもの): [RESOURCE-EXHAUSTION-AND-AVAILABILITY.md](RESOURCE-EXHAUSTION-AND-AVAILABILITY.md) を使う。
>
> **データ分離とライフサイクルのターゲット** (マルチテナントのストア、キャッシュ/検索、オブジェクトリンク、分析、エクスポート/バックアップ、マイグレーション、削除、保持、リストア): [DATA-ISOLATION-AND-LIFECYCLE.md](DATA-ISOLATION-AND-LIFECYCLE.md) を使う。
>
> **デスクトップ、モバイル、ローカル IPC のターゲット** (ネイティブアプリ、ディープリンク、webview ブリッジ、エクスポートされたコンポーネント、特権ヘルパー、ローカルデーモン、Unix ソケット/XPC/Binder/D-Bus): [DESKTOP-MOBILE-AND-LOCAL-IPC.md](DESKTOP-MOBILE-AND-LOCAL-IPC.md) を使う。

**Injection** (インジェクション、subagent_type: `general`)
信頼できない入力を、エントリーポイントから危険なシンクまで追跡する。何が「危険なシンク」に当たるかはアプリケーションによって異なる。
- Web アプリ: SQL クエリ、HTML 出力、シェルコマンド、テンプレートエンジン、ファイルパス、HTTP リダイレクト、デシリアライズ
- ライブラリ: 呼び出し元が渡したデータを検証せずに処理するあらゆる関数 — バッファ操作、パーサー、フォーマット文字列
- CLI ツール: シェルコマンドの構築、ファイルパスの扱い、環境変数の展開
- サービス: クエリの構築、メッセージのシリアライズ、ログインジェクション、LDAP/XPATH クエリ
- クライアントサイド (ブラウザ/JS): DOM XSS、プロトタイプ汚染、`postMessage`/オリジンの信頼、その他のブラウザ側のクラス — 選択された場合は [CLIENT-SIDE.md](CLIENT-SIDE.md) のコンパニオンブロックで扱う

明白な直接経路で止まってはならない。間接的なインジェクションを探す: 安全に保存されたデータが、別のコードによって取り出され、危険なコンテキストで使われるケースである。値だけでなく、フィールド名、キー、ヘッダー、メタデータを通じたインジェクションを探す。二次的なシステム (ログ、キャッシュ、検索インデックス、分析) へのインジェクションを探す。

**Access control** (アクセス制御、subagent_type: `general`)
呼び出し元が自身の権限外のことを行えないことを検証する。権限チェックが存在するかの確認にとどまらず、*正しい*リソースに対して*正しい*仕組みで*正しい*権限をチェックしているかを検証する。
- 同じ状態変更に至る経路で、別の (より弱い) 権限をチェックするものはないか?
- リクエストボディのフィールドで、権限システムが制限しようとしたものを上書きできないか?
- 認証では制限しているが認可を忘れているエンドポイントはないか?
- 同じリソースに、チェックが一貫しない複数のアクセス経路はないか?
- 一括/バッチ/エクスポート/インポート操作はどうか — 項目ごとの権限を強制しているか?

複雑なアクセスモデルでは、認証バイパスと認可ロジックを別々のエージェントに分ける。

**Resource and file handling** (リソースとファイルの扱い、subagent_type: `general`)
- パストラバーサル (意図したディレクトリ外の読み書き) — シンボリックリンク、エンコードされたシーケンス、ヌルバイトを介したものを含む
- SSRF (アプリケーションに攻撃者が制御する URL を取得させる) — リダイレクト、DNS リバインディング、URL パーサーの差異を介したものを含む
- 安全でないデシリアライズ、アーカイブ展開 (zip slip)、一時ファイルの扱い
- メモリ安全性 (該当する場合): バッファオーバーフロー、use-after-free、整数オーバーフロー
- ファイル操作の競合状態 (チェックと使用の間の TOCTOU)

**Cryptography and secrets** (暗号とシークレット、subagent_type: `general`)
- セキュリティ上重要な値 (トークン、鍵、nonce) に対する弱い乱数
- ハードコードされたシークレット、ログ、エラーメッセージ、URL、クライアントから見えるレスポンス中のシークレット
- 壊れた鍵導出、HMAC 検証の欠如、nonce の再利用
- シークレット比較におけるタイミングサイドチャネル
- 暗号プリミティブの誤用 (ECB モード、認証なしの暗号化、静的 IV など)
- 暗号処理が失敗したらどうなるか? エラー経路が暗号なしにフォールバックしないか?

**Business logic** (ビジネスロジック、subagent_type: `general`)
ロジックエラーは手作業で探す。標準的なスキャナーでは見つけられず、影響の大きい finding につながる。主要なワークフローごとに次を見る。
- **状態機械の違反**: ステップを飛ばせるか? 戻れるか? 無効な状態に到達できるか? 完了したフローをリプレイしたらどうなるか? 部分的な失敗はどうか — 3 ステップ中のステップ 2 が失敗したら、ステップ 1 はロールバックされるか?
- **ビジネスへの影響を伴う競合状態**: 無効な状態を生む並行操作 (二重支払い、二重承認、更新の消失)。check-then-act を非アトミックに行う操作に注目する。
- **数値/数量の操作**: 負の値、ゼロ、オーバーフロー、精度の損失、文字列と数値の間の型変換。
- **アクセス境界の違反**: 「権限チェックが存在するか」ではなく、「それがビジネスルールに対して正しいチェックか」。ある操作への入力で、同じ効果を持つ別の操作に課された制限を迂回できないか?
- **暗黙の信頼の前提**: ストレージ、設定、他のコンポーネント、プラグインからのデータが、「入るときに検証した」という理由で安全だと仮定されていないか。別のコード経路がそれを書き込んだらどうなるか?
- **時間に基づくロジック**: 有効期限チェック、スケジューリング、レートのウィンドウ、クロックのずれ。ちょうど境界の瞬間に何が起きるか? コンポーネント間のタイムゾーンの違いはどうか?
- **デフォルトとフォールバックの挙動**: 設定が欠けているときのセキュリティ態勢はどうか? フィーチャーフラグがオフのときは? 依存先が利用できないときは? システムがマイグレーションの途中のときは?

**Feature abuse and data leakage** (機能の悪用とデータ漏えい、subagent_type: `general`)
正当な機能が意図しない目的で使われるケース。コードだけでなく設計上のバグを探す。
- **流出手段としてのエクスポート/バックアップ**: 低権限ユーザーが、自身のアクセスレベルを超えるデータを含むエクスポート、スナップショット、バックアップを起動できるか? 他のユーザーのデータをエクスポートできるか? エクスポートに削除済み/下書き/非公開のコンテンツが含まれるか? 削除されるはずだったリビジョン履歴は?
- **インジェクション手段としてのインポート/リストア**: インポートで既存データを上書きできるか? 通常の検証を迂回するレコードを作成できるか? ユーザーが書き込み権限を持たないコレクションにコンテンツを注入できるか? UI と同じ権限モデルを守っているか?
- **オラクルとしての検索/フィルタ/ソート**: 検索クエリから、ユーザーが直接アクセスできないコンテンツの存在がわかるか? フィルタのパラメータで、知るべきでないステータス、ロール、フィールドを探れるか? 隠しフィールドでソートすると、結果の順序からその値がわかるか?
- **副作用による列挙**: 「存在しない」と「アクセス権がない」でエラーメッセージが異なるか? レスポンス時間は? レスポンスサイズは? HTTP ステータスコードは? パスワードリセット、招待、登録のフローを通じてユーザーを列挙できるか?
- **プレビュー/下書き/ステージングからの漏えい**: プレビュートークンは 1 項目にスコープされているか、それともより広いアクセスを開くか? 下書きコンテンツが、検索、RSS フィード、サイトマップ、API の一覧エンドポイントから発見できるか? キャッシュヘッダーによって CDN が非公開コンテンツを公開で配信してしまうことはないか?
- **SSRF としての通知/webhook**: ユーザーが、サーバーが取得する通知 URL、webhook URL、コールバック URL を設定できるか? 内部ネットワークに対して検証されているか? リダイレクト後はどうか?

**Chained vulnerabilities and trust boundaries** (連鎖する脆弱性と信頼境界、subagent_type: `general`)
個別には許可されている、あるいは封じ込められている挙動でも、別のコンポーネントやライフサイクルのステップがより強い保証に依存していると、脆弱性になり得る。
- **複数ステップにわたる境界の失敗**: 低権限の principal が読み取り、書き込み、呼び出し、保持できるものをマッピングし、具体的な出力だけを後続の信頼判断に結びつける。各前提条件を確認し、下流の影響を仮定してはならない。
- **コンポーネント間の信頼のギャップ**: コンポーネント A が入力を検証して B に渡す。A が生み出す正確な保証と B が仮定するものを、切り詰め、型変換、正規化、テナントスコープ、プラグイン/拡張機能のアクセスを含めて比較する。
- **二次的な使用**: 保存時に安全なデータが、後のコンテキストで危険になり得る。フィールド名が JSON パスになる、スラッグがファイルパスになる、エスケープされたテキストが生のレンダリングに入る、保存された文字列が URL、正規表現、テンプレート、ポリシー式になる、といったケースである。
- **スコープとケイパビリティの拡大**: トークン、API キー、プラグイン、OAuth、MCP、AI のケイパビリティが、委譲、リフレッシュ、キャッシュ、ロール変更、合成の後に広がる。結果として生じる principal が持つべきでない具体的な操作を明示する。
- **タイミングと順序**: セットアップ、マイグレーション、論理削除、失効/キャッシュの有効期限切れ、check/use、validate/consume のウィンドウをレビューする。報告する前に、古い状態が受け入れられることを確認する。
- **ロールバックと復旧**: 削除の取り消し、リストア、リビジョンのロールバック、キャンセルは、現在の所有権、検証、認可を適用しなければならない。どの無効な状態が復元されるかを確認する。

**Wildcard** (ワイルドカード、subagent_type: `general`)
カテゴリは与えられない。すでに割り当てられた標準クラス以外の脆弱性を見つける。

退屈に見えるコードや、セキュリティと無関係に見えるコードを読む。未完成、実験的、互換性用、フォールバックの機能を追うが、他のすべてのクラスと同じ具体的な境界と検証の要件を守る。

次の出発点を使うが、それに限定しない。
- コードベースで最も奇妙なコードは何か? なぜ存在するのか? 悪用されたら何が起きるか?
- 未完成、実験的、後付けに感じられる機能はないか? そうした機能はレビューが最も少ないため、セキュリティが最も弱い。
- フロントエンドが決してしない使い方で API を使ったらどうなるか? UI はユーザーを制約するが、API は制約しない。可能だがクライアントが決して行わない API 呼び出しは何か?
- 隠された、あるいは文書化されていないエンドポイント、パラメータ、ヘッダー、機能はないか? ルート登録、ミドルウェア、設定を見て、ドキュメントにないものを探す。
- 一緒に動くよう設計されていない機能を組み合わせたらどうなるか? ローカライズ + プレビュー + キャッシュ。インポート + プラグイン + webhook。OAuth + なりすまし + API キー。
- git の履歴に興味深いものはないか? 取り消されたセキュリティ修正、コメントアウトされた認証チェック、コミット後に削除された (履歴にはまだ残っている) シークレット。
- 有効なアカウントによるどの操作が、他のユーザー、共有の完全性、可用性、運用者負担のコストに影響するか? それらの操作の周辺で、封じ込め、クォータ、認可、復旧を検証する。
- どの操作が不可逆、あるいは高いレベルの確認を必要とするか? 認可と承認を、最終的な principal、操作、リソースに結びつける。
- コードは環境についてどんな前提を置いているか? データベースがローカルにある、時計が正確である、DNS が信頼できる、ファイルシステムが大文字小文字を区別する、といった前提である。
- テストファイルを見る — 何をテスト**していない**か? 開発者が考えたエッジケース (テストがある) と、考えなかったもの (テストがない) を比較する。

割り当てられたスコープ内の異常は、不変条件が確定するまで追う。何か奇妙に見えたら、安全かどうかを言えるまで読む。関数に、なぜ安全かを説明するコメントがあれば、その説明を検証する。変数が `temp`、`hack`、`legacy` という名前なら、よく読む。

**Obvious things** (明白なもの、subagent_type: `general`)
他のエージェントは微妙なバグを探す。このエージェントは、誰かがすでに確認したと皆が思い込むために見落とされやすい基本的な露出を確認する。
- ソースにハードコードされたパスワード、API キー、トークン、シークレットはないか? (`password`、`secret`、`apikey`、`token`、`Bearer`、`-----BEGIN`、一般的なデフォルトパスワードを grep する)
- セキュリティに言及する TODO/FIXME/HACK/XXX コメントはないか? (`TODO: add auth`、`FIXME: validate input`、`HACK: skip permission check`)
- デバッグモード / 開発モードは適切に制限されているか? 環境変数、クエリパラメータ、ヘッダーで本番環境で有効にできないか?
- 本番環境で使えてしまうテスト用/サンプル用/シード用の認証情報はないか?
- 保護されていない `/debug`、`/admin`、`/test`、`/status`、`/health`、`/metrics`、`/env`、`/.env`、`/config` エンドポイントはないか?
- リポジトリにチェックインされた `.env`、`.env.local`、`credentials.json`、`*.pem`、`*.key` ファイルはないか?
- `.gitignore` は実際にシークレット、アップロード、ローカル設定をカバーしているか?
- 依存関係は固定されているか? 依存関係ツリーに既知の CVE はないか? (ロックファイルを確認する)
- 動的な入力を伴う `eval()`、`exec()`、`child_process`、`Function()`、`vm.runInContext`、`import()` はないか?
- CORS ヘッダーが `*` や過度に緩い値に設定されていないか? `Access-Control-Allow-Credentials` がワイルドカードのオリジンと組み合わされていないか?
- cookie に `HttpOnly`、`Secure`、`SameSite` 属性が欠けていないか?
- オープンリダイレクトはないか? (`redirect`、`return`、`next`、`url`、`goto`、`continue` という名前のパラメータが、検証なしにリダイレクトに渡されていないか)
- TLS は強制されているか? HTTP のみのエンドポイントはないか?
- 本番環境のエラーレスポンスが、スタックトレース、内部パス、SQL エラーを返していないか?

このエージェントに創造性は要らない。徹底的に、文字どおりに行う必要がある。すべての項目を確認し、それぞれの結果を報告する。

**重要**: このエージェントが報告する finding については、表面的な見た目だけでなく、完全なコード経路を検証しなければならない。cookie に `HttpOnly` が欠けているなら、その cookie にセキュリティ上機微なデータが含まれるか、設計上 JS がそれを読む必要があるかを確認する。エラーメッセージにフィールド名が含まれるなら、そのフィールドに実際に機微なデータが入ることがあるかを確認する。フラグは finding ではない — 報告する前に影響を追跡する。
