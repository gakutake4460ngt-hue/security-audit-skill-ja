# サプライチェーンとリリースのハンティング

#### このファイルを使う場面

対象が、依存関係を解決する、信頼できないコントリビューションからビルドする、CI を実行する、リリース成果物を作成する、ビルドに署名または昇格 (promote) する、プラグインを読み込む、デプロイ済みソフトウェアを更新する場合にこのファイルを使う。この領域は、ソースや依存関係からユーザーが実行する成果物までの信頼の受け渡しを扱う。ローカルのバイナリローダー内部の欠陥には `MEMORY-SAFETY-AND-BINARY.md` を、ランタイムのワークロード権限には `CLOUD-AND-DEPLOYMENT.md` を使う。

大きな対象は、依存関係の解決、CI の分離、成果物の出所、リリースの認可、アップデーター/プラグインの信頼に分割する。

## 基本規律 (この領域のすべてのエージェントプロンプトに含める)

```
- A mutable or known-vulnerable dependency is not a finding by itself. Show who can influence resolution, which build consumes it, and what execution or release boundary follows.
- Follow integrity across every handoff: source identity, resolved inputs, build worker, artifact identity, test result, signature/attestation, promotion, and update consumer.
- CI configuration is authorization code. Establish which event triggered a workflow, whose code runs, which secrets and tokens exist, and what it may publish or mutate.
- A checksum fetched from the same untrusted location as the artifact does not establish independent integrity. Identify the trusted root and failure behavior.
- Use `confirmed` for in-repo control-flow failures with bounded local validation. Use `needs_validation` for branch protection, hosted-runner, registry, signing-service, or production promotion facts that are not observable.
```

## 依存関係とビルド入力の攻撃クラス (subagent_type: `general`)

**依存関係のソースと名前空間の混同**
リゾルバーの設定により、意図しない公開/非公開の名前空間、フォールバックのレジストリ、ミラー、リポジトリ、ソース URL が選択されうる。パッケージ名、ソースの優先順位、ロックファイルとチェックサムの利用、別のビルドファイル、プラットフォーム固有の解決、初回インストールと更新時の挙動の違いをレビューする。

**可変で束縛されていないビルド入力**
ビルドが、ブランチ、タグ、未検証のサブモジュール、ダウンロードしたツール、生成されたアセット、リモートインクルード、固定されていない CI アクション、コンテナタグなど、ソースレビューなしに内容が変わりうるものを消費する。より信頼度の低い書き込み主体と、信頼されたビルド出力への経路を要件とする。再現性だけでは真正性は証明されない。

**生成ソースとコード生成の出所の欠落**
スキーマ、ベンダリングされたアーカイブ、生成されたクライアント、ローカライゼーション、ドキュメントの例、バイナリ blob が、ソースと同じレビューと完全性のゲートを経ずに、実行される、または出荷されるコンテンツを生み出す。ローカルでの再生成結果とコミット済みの出力を比較し、入力とジェネレーターを誰が制御するかを検証する。

**ビルドコンテキストへの混入**
ビルドコンテキストと除外ルールが意図したリリース入力を超えているため、秘密情報、ローカル設定、リポジトリのメタデータ、テストフィクスチャ、開発者の成果物がパッケージやイメージに入る。結果の成果物が実際のクレデンシャル、非公開データ、特権的な設定を露出することを確認する。

## CI と自動化の攻撃クラス (subagent_type: `general`)

**特権ワークフローでの信頼できないコード**
プルリクエスト、issue コメント、フォーク、依存関係の更新、外部イベントが、保護された秘密情報、書き込みトークン、デプロイ権限、信頼されたランナーを伴ってコントリビューターが制御するコードを実行する。トリガー種別、チェックアウトする ref、承認ゲート、environment の保護、権限の絞り込みを比較する。ソースにないリポジトリホストのデフォルトを前提にしない。

**ワークフローのコマンドと式の混同**
攻撃者が制御するブランチ名、コミットメッセージ、issue のフィールド、成果物名、マトリクスの値、生成された出力が、正規の検証なしにシェルコマンド、テンプレート式、パス、特権ワークフローの入力に入る。

**キャッシュ・成果物・ワークスペースの信頼の混在**
より信頼度の低いジョブが、キャッシュ、成果物、共有ワークスペース、出力を書き込め、より信頼度の高いジョブが後でそれを復元して実行またはリリースする。キャッシュキーと名前空間、成果物のプロデューサーの ID、ダイジェストへの束縛、保持期間、昇格時に可変の名前で再解決するかをレビューする。

**自動化 ID の権限過剰**
CI ジョブが、必要な操作、リポジトリ、environment、期間を超える権限を受け取り、信頼できないジョブ入力が影響を受けるリソースを選択できる。最小権限の欠如だけならハードニングである。到達可能な特権アクションを要件とする。

## リリースと更新の攻撃クラス (subagent_type: `general`)

**ビルドから昇格までのすり替え**
テスト、レビュー、署名、公開が、同じ不変のダイジェストではなく、可変のタグ、ファイル名、チャネル、成果物 ID を参照する。ビルドとリリースの間のすべてのコピー、再パッケージ、アーキテクチャの統合、出所記録のステップを確認する。

**リリース認可と署名ポリシーの欠落**
誤ったワークフロー、リポジトリ、ブランチ、environment、鍵のロール、しきい値からのリリースや署名が受け入れられる。attestation 内の ID の主張をレビューし、有効な署名だけでなくそれらの主張をコンシューマーが検証していることを確かめる。ポリシーが要求する場合、ローテーション、有効期限、失効はフェイルクローズでなければならない。

**更新メタデータとロールバックの混同**
アップデーターがペイロードのバイト列は認証するが、バージョン、プロダクト、プラットフォーム、チャネル、対象パス、有効期限、ロールバック状態を認証しない、または別々の認可済みトランザクションからのメタデータとペイロードを受け入れる。アトミックなインストールと復旧の挙動を検証する。ポリシーへの束縛のない署名 API 呼び出しは不完全である。

**プラグインと拡張機能の信頼拡大**
拡張パッケージが宣言されたスコープを超えるホスト権限を得る、より信頼度の低いパブリッシャーが別のパブリッシャーの ID を置き換えられる、またはインストール/更新フックが真正性とケイパビリティのチェックより前に実行される。同一ユーザーによる任意プラグインの意図的なインストールは、権限境界ではない。

## 共通の手順 (上記すべてに適用)

- リリースされたダイジェストやインストールされた更新から逆向きに、すべてのソース、生成された入力、クレデンシャル、ワーカー、キャッシュ、テスト結果、認可判断までたどる。
- 信頼できないワークフローイベントと保護されたワークフローイベントを並べて比較する。両者の間を越える永続化されたチャネルをそれぞれ記録し、不変の ID とプロデューサーの信頼を要件とする。
- 失効した鍵、ダウンロード失敗、欠落した attestation、一部プラットフォームのみのリリース、ロールバック、レジストリ障害の経路をレビューする。失敗時のポリシーはリリースの完全性の一部である。

## 検証ルール (ここでの指摘を報告する前に必ず適用)

1. より信頼度の低いアクター、制御可能なソース/キャッシュ/成果物/メタデータ、それを消費する信頼されたジョブまたはアップデーター、結果として生じる認可されていない公開、コードの混入、秘密情報の開示、特権実行を示す。
2. 破られた受け渡しをまたいで成果物の同一性を証明する。異なる可変の名前や束縛されていないダイジェストが、実際のコンシューマーに到達しなければならない。
3. 固定されたバージョンについて、パッケージマネージャー、リポジトリホスト、レジストリ、署名の組み込みデフォルトを検証する。ホスティング側の制御が不明な場合は `needs_validation` とする。
4. ローカルでの検証は範囲を限る。無害なフィクスチャリポジトリ、ダミーのクレデンシャルマーカー、ローカルのレジストリ/設定、本番ではない成果物の名前空間を使う。実際のリリースを公開したり変更したりしない。
5. `confirmed` は、ソースから見える完全な受け渡しと意味のある結果がある場合にのみ返す。オーナーが観測すべきブランチ、ランナー、レジストリ、署名、デプロイに関する事実を正確に添えて `needs_validation` を返す。
