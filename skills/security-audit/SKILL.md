# セキュリティ監査

実際の信頼境界を侵害する脆弱性を見つけ、オーナーにソース上の証拠、安全な再現手順、優先度、最小限で効果のある修正を示す。これはソースを起点とする防御的なワークフローである。影響を受ける具体的なプリンシパル、リソース、セキュリティ上の結果を伴わない候補は、確定した指摘ではない。

## 動作モード

このスキルはデフォルトではガイダンスである。読み込んだだけでは、完全な監査ワークフローの実行やファイル作成は許可されない。

- **ガイダンスモード**: セキュリティに関する質問、焦点を絞ったレビュー、方法論、トリアージ、特定の指摘の調査では、このスキルの該当部分だけを使う。6 つのフェーズを自動的にすべて実行したり、出力ディレクトリを作成したり、監査成果物を書き出したりしない。有用であれば焦点を絞ったエージェントを起動してよい。その結果は現在のタスクに返される。
- **フル監査モード**: ユーザーがコードベースの監査またはペネトレーションテストを明示的に依頼した場合、完全・包括的・エンドツーエンドのセキュリティレビューを依頼した場合、またはレポート成果物を求めた場合に、完全なワークフローを使う。6 つのフェーズをすべて実行し、以下で定義するファイルを書き出す。

依頼がどちらのモードとも解釈できる場合は、ファイルを作成したり完全なワークフローを開始したりする前に、焦点を絞った質問を 1 つする。

## プラットフォーム用語

このスキルは特定のエージェントに依存しない。

- **Parent** は実行を統括し、共有状態を所有するエージェントである。
- **Task tool** は、プラットフォームが提供する委任またはサブエージェントの仕組みである。
- **`research` agent** は、焦点を絞ったソース探索と事実確認のために委任されるエージェントである。
- **`general` agent** は、広範な調査と範囲を限定したローカル実行のために委任されるエージェントである。
- 見出し中の **`subagent_type:`** は、その作業をこれら 2 つの委任エージェントのどちらの役割が実行するかを示す。

役割、書き込み分離、プロンプト、独立性の境界を保ったまま、プラットフォーム上の同等の機能を使う。

## 共通の実行上の安全規則

これらの規則は両方の動作モードに適用される。ソースの調査は読み取り専用で行う。ターゲットが制御するビルド、テスト、プロセス、ブラウザ、エミュレータ、ファザー、フィクスチャ処理は、次のすべての制御を備えた OS 強制のサンドボックス内でのみ実行する。

- 外部ネットワークなし。検証にローカルのクライアント/サーバー通信が必要な場合のみ、分離されたループバック名前空間を使う。
- 安全な値の明示的な許可リストから構成した空の環境。`HOME`、一時ディレクトリ、キャッシュはスクラッチ内に置く。
- ターゲットとツールチェーンは読み取り専用とし、ターゲットが制御するプロセスは割り当てられた `scratch/` ディレクトリ内にのみ書き込める。
- CPU、メモリ、プロセス数、ファイルサイズ、ディスク、実時間に対する明示的で低い上限。

ビルドがソースの隣に書き込む必要がある場合、エージェントはターゲットが制御するプロセスの外側で、割り当てられた `scratch/` ディレクトリに使い捨てのソースコピーを作ってよい。ガイダンスモードでは、ターゲットが制御するファイルを保持しない。フル監査モードでは、信頼された Parent 側のコードだけが、「書き込み分離」の手順に従って、秘密情報を含まない最小限の結果を保持用の `artifacts/` に昇格できる。保持用の出力ディレクトリ (エージェント自身に割り当てられた `scratch/` を除く)、他のエージェントのディレクトリ、ホストのホームディレクトリ、認証情報、ソケット、共有サービスを、ターゲットのコードに決して公開しない。依存関係をインストールしたり、ビルドに取得させたりしない。ローカルにすでにあるツールと依存関係だけを使う。いずれかの制御を強制できない場合は、ターゲットのコードを実行しない。不足しているサンドボックス機能を needs-validation のブロッカーとして報告し、安全な検証計画を示す。

ダミーのプリンシパル、フィクスチャ、秘密情報を使う。デプロイ済みのエンドポイント、外部サービス、共有インフラ、本番の ID、他のユーザーのデータ、稼働中のコントロールプレーンを調べない。稼働中または共有のプロセスに対して可用性をテストしない。成果物を公開したり、リリースを変更したり、有料 API のクォータを消費したり、欠陥を立証するのに必要な最小限のローカルな影響を超えて続けたりしない。決定的な事実がソースやサンドボックス内のフィクスチャの外にある場合は、検証が必要なものとして報告する。

## フル監査のセットアップ

フル監査モードでは、偵察の前に次の値を確定する。

- **スキルディレクトリ**: この `SKILL.md` を含むディレクトリの絶対パス。
- **ターゲット**: レビュー対象リポジトリのルートの絶対パス。
- **リポジトリ名**: ディレクトリ名またはローカルの Git リモートから得る、安定したリポジトリ識別子。
- **出力ディレクトリ**: ターゲットの外にある、新しい書き込み可能なディレクトリ。デフォルトは `~/security-audit-skill/<repo-name>/run-<N>` で、`<N>` は未使用の次の整数である。ターゲット内のディレクトリを使うのは、ユーザーが明示的にそれを選び、かつ Parent がそのディレクトリ全体がバージョン管理で無視されることを確認した場合だけである。それ以外の場合は停止し、外部のパスを求める。
- **ソース ref**: レビュー対象のコミットと、ワークツリーがダーティかどうか。レビューしていない生成ファイルや変更済みファイルを別のリビジョンとして扱わない。

### 書き込み分離

共有の実行ファイルは Parent が作成し、Parent だけが書き込む。

- `run-metadata.json`
- `architecture.md`
- `coverage-ledger.json`
- `findings.json`
- `REPORT.md`
- `FINDINGS-DETAIL.md`
- `NEEDS-VALIDATION.md`

各ハンターと検証者には `<output-dir>/agents/<agent-id>/` 配下に固有のルートが与えられ、その中に `scratch/` と `artifacts/` が別々に置かれる。正規のエージェント ID は `^[a-z0-9][a-z0-9_-]{0,63}$` に一致しなければならず、`con`、`prn`、`aux`、`nul`、`com1` から `com9`、`lpt1` から `lpt9` などの Windows のデバイス名と同じであってはならない。小文字の ID にすることで、大文字小文字の畳み込みによる衝突を防ぐ。エージェントとターゲットが制御するすべてのプロセスは `scratch/` にのみ書き込める。保持用の `artifacts/` は Parent が所有し、サンドボックスには決して公開されず、信頼された Parent 側の昇格コードだけが書き込める。エージェントは共有ファイル、ターゲットのソース、保持された成果物、他のエージェントのディレクトリを変更してはならない。書き込み可能な代替先として `/tmp` やホストのホームディレクトリを使わない。

実行前に、Parent はエージェントの `scratch/` と `artifacts/` のルートに対する信頼された継承不可のディレクトリディスクリプタを開いて保持し、想定される scratch 相対の成果物ファイルの許可リストと、ファイルごとおよび累積の明示的なバイト上限を記録する。これらのディスクリプタをエージェントやサンドボックスに決して渡さない。サンドボックスとそのすべてのプロセスが終了した後、信頼された Parent 側のコードが、許可リストの各ファイルを個別に昇格する。

1. 宣言された相対パスを検証する。絶対パス、空、`.`、`..`、シンボリックリンクの構成要素を拒否する。
2. 保持している scratch ルートのディスクリプタから、リンクをたどらないディレクトリ相対の操作で親の各構成要素をたどる。パスで開き直すことは決してしない。
3. 末端をリンクをたどらず、ノンブロッキングで開く。
4. `fstat` で、それが通常ファイルであり、リンク数がちょうど 1 で、記録したファイルごとおよび累積のバイト上限内であることを確認する。
5. そのディスクリプタから読み取る間も、これらの上限を再度強制する。
6. 確認したサイズちょうどをコピーし、`fstat` を繰り返し、同一性、種類、リンク数、サイズが変化していれば拒否する。
7. コピー先については、保持している artifacts ルートのディスクリプタから、リンクをたどらないディレクトリ相対の操作で親の各構成要素をたどる。既存の各構成要素が実際のディレクトリであることを要求し、存在しないディレクトリは排他的に作成してから、リンクをたどらずに開き直して確認する。
8. リンクをたどらずに末端を排他的に作成し、開いたコピー先がリンク数ちょうど 1 の通常ファイルであることを確認し、どちらのパスも開き直さずに、確認済みのコピー元ディスクリプタからコピーする。
9. 非 POSIX システムでは、同等の競合に安全な API を使う。
10. scratch を再帰的にコピーしたり glob したり、アーカイブを artifacts に展開したり、シンボリックリンク、FIFO、ソケット、デバイス、ディレクトリ、ハードリンクされたファイル、変化中のファイル、上限を超えるファイルを開いたり昇格したりすることは決してしない。
11. いずれかのチェックが利用できない、強制できない、または失敗した場合は、その scratch のエントリを破棄する。それが決定的な証拠であれば、正確な昇格ブロッカーを付けて `needs_validation` として保持する。

[HUNTING.md](HUNTING.md) と [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md) は、ハンターと検証者のプロンプト用にこの手順を同一のフェンスブロック 1 つとして収録している。そのブロックは、このリストと同じ規則を同じ順序で述べている。

再現したチェックについては、コマンド、正確なテスト入力、サンドボックスの上限、および再現に必要な許可リスト上の環境変数名と安全で秘密でない値だけを記録する。周囲の環境、継承された変数、認証情報の値、認証状態、無関係なホストのパスを決して取得・コピーしない。実行後に環境を伏せ字にしようとするのではなく、空の環境から起動する。

委任の前に、Parent は少なくとも `run_id`、`repo`、`target`、`source_ref`、`profile`、`scope_paths`、`budget` (未設定なら null)、`execution_policy: "sandboxed-source-and-local-only"`、選択したコンパニオンファイル、過去の実行のパス、共有ファイルのオーナー、`run_status: "in_progress"` を含む `run-metadata.json` を書き出す。メタデータは、これらの事実が変わったときにだけ更新する。候補の状態はカバレッジ台帳と `findings.json` に置く。

## フル監査の計画

この節のカバレッジ、過去の実行、プロファイル、予算に関する要件は、フル監査モードにのみ適用される。

### カバレッジと過去の実行

1 回のパスで完結するものはない。ハンティングの前に決定的なカバレッジ計画を立て、エージェントの結果が出るたびに更新する。[RECONNAISSANCE.md](RECONNAISSANCE.md) は安定したカバレッジ単位を定義し、[HUNTING.md](HUNTING.md) はカバレッジ批評ウェーブを定義する。台帳を更新するのは Parent だけである。

過去の実行が存在する場合は、今回の実行を計画する前に、互換性のあるすべての `coverage-ledger.json` と `findings.json` を読む。

1. 関連する現在のソースを、過去の各レコードおよび各単位と比較する。過去のソース ref だけでは、パスが変わっていない証拠にはならない。
2. 過去の `confirmed` レコードを今回の候補集合に引き継ぐのは、その関連ソースと条件が変わっておらず、その証拠が現在の契約をなお満たす場合に限る。それを `planned` で初期化した現在の台帳単位にリンクし、そのフィンガープリントを保持し、引き継いだその根本原因だけをハンターから除外し、引き継いだレコードを現在の最終検証経路に通す。それを再確認する Phase 3 の検証者がその単位の割り当てオーナーとなり、単位を `candidate` に移す。
3. 過去の `confirmed` レコードの関連ソースが変わった場合は、現在の計画済み再検証単位を作成する。そのレコードをハンターの除外リストに入れない。現在の独立した検証が現在の経路と結果を立証した場合にのみ、confirmed のままとなる。
4. 過去の `needs_validation`、`deferred`、`blocked`、`out_of_scope`、およびソースが変わった単位を現在の作業とする。依然として外部要因に依存する `needs_validation` レコードを引き継げるのは、現在のソーストレースを確認し、フィンガープリントで現在の `planned` 単位にリンクした後に限る。その単位の検証者による再確認がオーナーと証拠を提供する。レコードは未解決のブロッカーを保持する。これら過去の状態が現在の単位を抑制することは決してない。
5. 過去の同一ソースでカバー済みの単位は優先度の参考にしてよいが、現在の台帳では見えるままにしておく。過去の `rejected` レコードが抑制するのは変更されていない不成立の主張だけであり、その単位のカバレッジではない。証拠が変われば現在の作業になる。
6. 過去のプロファイルとスコープを読む。過去の `quick` またはスコープ限定の台帳が寄与するのは、記録された証拠とギャップだけであり、「残りは問題ない」という含意は決して生じない。

過去の台帳が存在しない場合は、最終的なカバレッジの記述でその旨を述べる。1 回の実行でターゲットを網羅したかのように示唆しない。

### 実行プロファイルとスコープ

フル監査のセットアップ中に、ユーザーの依頼からプロファイルを選ぶか、ターゲットの規模と重要度からプロファイルを提案する。それを `run-metadata.json` (`profile`、`scope_paths`) に記録し、レポートに明記する。デフォルトは `standard` である。

- **`quick`** — 小規模なターゲット、再実行、素早い初回確認のための範囲を限定したパス。台帳単位を surface × boundary × attack class に粗くし (subsystem には固定の正規識別子 `profile/quick/all-in-scope-subsystems` を使う)、ハンターウェーブをちょうど 1 回実行した後に最終カバレッジ批評パスをちょうど 1 回実行し、候補の検証と最終レコードの検証の両方に、候補ごとに新しい検証者を 1 つ使う。後続のハンターウェーブは起動しない。批評者が受理した発見と再割り当ては `deferred` として記録する。
- **`standard`** — 記述どおりのワークフロー。
- **`deep`** — 重要度が高い、または大規模なターゲット向け。台帳単位をサブシステムとライフサイクルモードごとに分割し、クリーンなパスになるまで批評ウェーブを実行し、候補の検証と最終レコードの検証を別々の新しいエージェントで行い、`prior_covered_same_source` 単位には独立した 2 回目のパスを与える。

**スコープ限定の実行**は部分集合を監査する。名前を指定したパス、1 つのサブシステム、1 つのコンパニオンドメイン、または 2 つのソース ref 間の差分である。スコープ内のサーフェスに対してだけ台帳単位を初期化し、それ以外はすべて `out_of_scope` として記録する。決して `covered` にはしない。スコープ限定または `quick` の実行は、部分的なカバレッジであることを明示しなければならない。

プロファイルが変えるのは範囲と冗長性であり、証拠の基準は決して変えない。候補ゲート、ソース/ローカル実行の境界、`needs_validation` の規律、スキーマ検証、`confirmed` レコードの独立した検証を縮小しない。

#### コスト予算

台帳によって支出を数えられるようになる。1 単位はおおよそ 1 回のハンター割り当てであり、生き残った 1 候補はプロファイルに応じて 1 回または 2 回の検証者割り当てである。ユーザーが予算を設定した場合、または大規模なターゲットに対して Parent が予算を提案した場合は、`budget` を全フェーズを通じたエージェント起動回数の上限として `run-metadata.json` に記録する。

偵察エージェントを起動する前に、厳格な予算ゲートを適用する。基本の偵察呼び出し 4 回、`quick` では最終のウェーブ後批評者 1 回、`standard`/`deep` ではウェーブ後批評者 1 回と別個の最終クリーン批評者 1 回、および少なくとも 1 回の検証者呼び出しを確保する。追加の偵察は、追加呼び出しごとにこのゲートを繰り返した後にだけ加える。要求された予算でこの最低限をまかなえない場合は、エージェントを起動しない。より大きな予算、より狭いスコープ、または別のプロファイルを求める。依頼が変わらない場合は、`run_status: "incomplete"` と `incomplete_reason: "budget_cannot_fund_reconnaissance_and_reserves"` を設定し、監査パスを 1 つも実行しなかったと報告する。

予算は次の順序で使う。

1. 偵察、すべてのウェーブ後批評者、別個の最終クリーン批評者をエージェント起動として数える。
2. **ハンティングの前に批評と検証の分を確保する。** `quick` では、その 1 回のウェーブ後最終批評者を確保する。`standard` または `deep` の各ハンターウェーブの前に、直後のウェーブ後批評者 1 回と、別個の最終クリーン批評者 1 回を確保する。さらにプロファイルに応じた検証者のコストを確保する (想定される候補 1 件あたり約 1 または 2 エージェント。迷う場合は批評者の確保後の残高の 30% を確保する)。どちらの確保分にもハンターを割り当てない。
3. ハンティングに使える分を使い切るまで、優先順位の順に単位へハンターを割り当てる。確保したウェーブ後批評者はそのウェーブの直後に使う。最終クリーンと検証の確保分は手を付けずに残す。
4. 後続のウェーブの前に、その新しいウェーブ後批評者の分を再び確保する。残りの予算で必要な批評者呼び出しと検証の確保分をまかなえない場合は、そのウェーブのハンターを起動せず、その計画済み単位を理由 `budget_cannot_reserve_critics_and_validation` とともに `deferred` にし、残しておいた最終クリーン批評者を使って結果として生じたギャップを記録する。

ウェーブ 1 の前に、偵察前の見積もりを、初期化した単位、それに伴うハンター数、必須の批評者呼び出し、検証の確保分、残りの予算で計画をまかなえるかどうかで更新する。明らかにまかなえない場合は、その旨を述べ、証拠を黙って薄めるのではなく、より厳しいスコープかより粗いプロファイルのどちらかを提案する。後から判明した事実によって必要な最終批評者の確保分が消費された場合は、ハンターを起動せず、計画済みのすべての作業を deferred にし、理由 `critic_budget_exhausted` で実行を incomplete とし、完全なカバレッジを主張しない。

厳格なエージェント総数の予算であっても、想定外に大きな候補集合や、別の独立した検証者を必要とする Phase 5 の実質的な置き換えによって超過することがある。残りの予算ですべての候補を検証できない場合は、ハンティングを停止し、予算が許す限りフィンガープリント順に候補を検証し、`run_status: "incomplete"` と `incomplete_reason: "validation_budget_exhausted"` を設定する。未検証の各フィンガープリントを、その未解決の理由とともに `candidate` の台帳単位にリンクしたままにする。未検証の候補を `findings.json` に入れたり、`needs_validation` に付け替えたり、実行を完了として報告したりしない。Phase 6 で部分的なレポートを作成してよいのは、その最初の節で候補の検証が未完了であることを述べ、影響を受けるフィンガープリントと単位を列挙する場合だけである。ユーザーが設定した厳格な予算を黙って超えることは決してしない。

## 基本原則

### 境界と結果を要求する

すべての候補について、低信頼のプリンシパル、受け付けられる入力または操作、意図された制御、越えられた境界、影響を受けるプリンシパルまたはリソース、具体的に観測された、またはオーナーが観測可能な結果を明示する。ベストプラクティスの欠如、推測したデプロイ時の挙動、一般的なパーサーのクラッシュ、自己への影響をセキュリティ上の指摘に格上げしない。

### 範囲を限定したローカルの証拠を使う

静的解析はソース上の経路を立証する。すべての実行制御が利用可能な場合は、サンドボックス内のローカルテストで挙動を確定する。最小限の関数ハーネス、既存の単体テスト、小さなパーサーフィクスチャ、ダミーテナントの統合テスト、ローカルで生成した設定、範囲を限定した分離ループバッククライアントなどである。誤った戻り値、権限のないダミーレコード、サニタイザーの検出、ポリシーの差異、その他の最小限の影響で止める。ローカルのチェックを最小限の境界上の結果を超えて拡張したり、永続化、障害発生後、隠蔽のための材料を作成したりしない。

### ソースの可視性を尊重する

デプロイ時の制御、プロキシの挙動、プロバイダーの設定、ブラウザのヘッダー、ID ポリシー、ブローカーの ACL、パッケージング、トポロジーは実際の制御である。それらが必要であり、かつリポジトリに含まれていない場合は、存在も不在も仮定しない。正確な欠落事実と、安全なオーナー観測またはローカルの計画を付けて `needs_validation` を使う。

### 優先度と確実性を区別する

深刻度が付くのは `confirmed` レコードだけである。可能性と影響は、立証された条件と結果を反映しなければならない。全体の深刻度は立証された影響を超えられない。`needs_validation` は、ソースに根拠のある特定の境界仮説が阻まれていることを意味し、確信度の低い確定した脆弱性ではない。深刻度は持たない。

全体の深刻度は次の基準で調整する。

- **critical** — 未認証のアクターが、コード実行、データストア全体へのアクセス、または任意のアカウントの乗っ取りを得る。
- **high** — アクターが、実際の結果を伴う明示的なセキュリティ制御を完全に破る。認証バイパス、テナント間の読み取りまたは書き込み、他のユーザーに影響する格納型スクリプト実行、認証済みのコード実行、共有サービスの未認証リモート停止などである。
- **medium** — 影響範囲が限られる、前提条件がまれである、または結果が狭いリソース集合に限定される、実際の境界侵害。
- **low** — 秘密でない内部情報の開示、または最小限の利益のために持続的な労力を要する影響。
- **informational** — 確定しているが影響が最小限の観察。主に、より大きな指摘の中の前提条件として有用である。

high と medium の判別基準: 立証された結果は、実際の結果を伴う操作に対する明示的な制御を完全に破るのか、それとも弱めるだけなのか。具体的な損害を述べられないなら、深刻度は感覚よりも低い。

### 最小限で効果のあるソース修正を推奨する

確定した各指摘について、コードが強制すべき不変条件と、最後の信頼された判断点でそれを強制する最も狭いソース変更を特定する。一般的なハードニングの助言よりも、リポジトリ相対の具体的な変更と回帰テストを優先する。監査は修正を記述するが、ターゲットのソースは変更しない。

## フル監査のワークフロー

フル監査モードでは、6 つのフェーズをすべて順に実行する。

1. **偵察** — [RECONNAISSANCE.md](RECONNAISSANCE.md) を使って、ソース、信頼境界、ローカルのビルド経路、コンパニオンの選択、過去の証拠、初期の決定的なカバレッジ台帳を把握する。
2. **カバレッジ主導のハンティングウェーブ** — [HUNTING.md](HUNTING.md)、[ATTACK-CLASSES.md](ATTACK-CLASSES.md)、選択したドメインコンパニオンを使って、台帳から分離されたハンターを割り当て、構造化された候補結果を収集する。
3. **候補の検証** — [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md) の定義に従って、フィンガープリントを統合し、すべての候補を新しいソース検証者に渡す。
4. **構造化出力** — 最終的なすべての `confirmed`、`needs_validation`、`rejected` レコードを `findings.json` に書き出す。それを `report-schema.json` と `validate-findings.cjs` で検証し、カバレッジの主張を `validate-coverage-ledger.cjs` で検証する。
5. **独立したレコード検証** — 新しいエージェントを使って最終的なソース上の主張を検証し、修正や状態の変更を調整する。
6. **ターゲット中立のレポート** — 最終レコードから `REPORT.md`、`FINDINGS-DETAIL.md`、`NEEDS-VALIDATION.md` を導出する。稼働中のターゲットを調べる手順は含めない。

ちょうど 2 つの終了状態のいずれかに達する前に実行を終えない。(a) Phase 6 のすべての成果物が書き出され、両方のバリデーターが成功する、または (b) 正確な理由とともに `run_status: "incomplete"` が記録され、そのギャップがレポートで開示される。フェーズの途中で決して停止しない。

## アンチパターン

1. チェックリストからの逸脱を脆弱性として提示する。
2. 到達可能な境界侵害のない多層防御の助言。
3. 範囲を限定したローカルの証拠では不十分な場合に、稼働中または共有の環境でテストする。
4. ソースに含まれていないプロバイダー、プロキシ、ブラウザ、ID、デプロイの挙動を推測する。
5. 意図された同一プリンシパルの権限や自己への影響を、境界を越える結果として扱う。
6. 観測された影響よりも強いパーサーまたはランタイムの影響を報告する。
7. 重複排除も検証もできない、文章だけのハンター結果を出力する。
8. 引き継いだ同一ソースの過去の confirmed レコードを再報告する、またはそれをハンティングの基準となる見本として使う。
9. `needs_validation` レコードに深刻度を付ける。
10. 独立した検証の前にレポートを書く、または文章と JSON の食い違いを放置する。
