# HTTP プロトコルと認証の調査

#### このファイルを使う場面

対象がパース、キャッシュ、ブラウザ認証、アイデンティティのいずれかの境界で HTTP を扱う場合にこのファイルを使う。具体的には Web アプリケーション、API、リバースプロキシ、CDN、ゲートウェイ、独自 HTTP サーバー、そしてセッション、JWT、OAuth/OIDC、SAML、パスワード回復、MFA、パスキー、API キー、mTLS を実装するサービスである。`ATTACK-CLASSES.md` と併用する。アクセス制御のレビューは「あるプリンシパルがある操作を実行してよいか」を問う。このファイルは「HTTP 層やアイデンティティ層が、その操作がどのプリンシパル、リクエスト、保証レベル、トークンに属するかを取り違えさせ得るか」を問う。

Phase 1 からクラスを選ぶ。大きな対象は、リクエストのフレーミングとキャッシュポリシー、ブラウザ認証、フェデレーテッドアイデンティティ、強力な認証と回復、サービスクレデンシャル、セッションライフサイクルに分割する。観測できないマネージドプロキシの背後にある単一サーバーには、ソースで確認できるスマグリングの攻撃面はほとんどない。プロキシや独自パーサーにははるかに多い。

## 基本原則 (このドメインのすべてのエージェントプロンプトに含める)

```
- Framing and cache findings require two interpretations of the same request, response, or key. Name both components and the exact normalized value on each side.
- For every credential, find the signature or secret verification and every binding required for its role: issuer, audience, origin, RP, client, session, principal, resource, assurance, expiry, and one-time state.
- Host, Forwarded, X-Forwarded-*, Origin, Referer, redirect targets, callback state, and request-derived URLs are trust decisions. Trace each to the affected identity or response.
- A missing header, cookie attribute, MFA prompt, or rate limit is not a finding alone. Require an accepted invalid request, cross-principal impact, assurance downgrade, or credential disclosure.
- Classify `confirmed` only from complete source evidence and bounded local request/token tests. Use `needs_validation` when proxy, IdP, browser, certificate, secret, or deployed configuration is required but not visible.
```

## HTTP フレーミングとキャッシュの攻撃クラス (subagent_type: `general`)

**リクエストのフレーミングと非同期化 (desync)**
フロントエンドとバックエンドで、リクエスト長やヘッダー正規化の解釈が食い違う。複数の `Content-Length` 値、`Transfer-Encoding`、HTTP/2 や HTTP/3 からのダウングレード、ヘッダー名の正規化、禁止された接続ヘッダー、CR/LF 変換をレビューする。あるコンポーネントがどのバイトをリクエストに割り当て、その相手側がどのバイトを次のリクエストに割り当てるかを確認する。

**キーに含まれない入力による Web キャッシュポイズニング**
あるリクエスト値がキャッシュされるコンテンツやセキュリティ上重要なヘッダーを変えるのに、キャッシュキーには含まれない。キャッシュキーの構築とすべてのレスポンスバリアントを比較する。転送されたホスト/スキーム、選択された Cookie、クエリの正規化、言語/デバイスヘッダー、認可状態も含める。

**キャッシュデセプションとプライベートレスポンスのキャッシュ**
キャッシュのルーティングがプライベートな動的パスを公開の静的アセットとして扱う、あるいはアイデンティティや認可の入力がポリシーから欠けたレスポンスをキャッシュする。エッジのキャッシュ可否と、アプリケーションのルートパース、サフィックス/パスパラメーターの正規化、レスポンスのキャッシュディレクティブを比較する。

**Host ヘッダーと転送ヘッダーの信頼**
信頼できないホスト/プロキシのメタデータが、絶対 URL、テナントルーティング、コールバック、リセットリンク、キャッシュキー、または認可に使うクライアントアドレスを決める。誰がそのヘッダーを供給できるか、信頼されたイングレスがクライアントから送られたコピーを除去するかを確認する。

**レスポンスヘッダーインジェクション**
信頼できないデータが、危険な制御文字や正規化を伴って `Location`、`Set-Cookie`、CSP などのレスポンスヘッダーに到達する。報告前にフレームワークが拒否するかを確認し、セキュリティ上意味のあるレスポンスの変化を要件とする。

## ブラウザセッションの攻撃クラス (subagent_type: `general`)

**通常の CSRF**
ブラウザがアンビエントクレデンシャルを状態変更エンドポイントに送り、そのエンドポイントが有効な anti-CSRF トークン、same-site のリクエスト束縛、厳格な Origin/Referer 検証なしにクロスサイトリクエストを受け入れる。Cookie で認証されるすべての変更操作を洗い出す。フォーム、JSON 風、multipart、メソッドオーバーライド、レガシーのルートも含める。SameSite が有効なのは、実際に使われる Cookie とブラウザコンテキストに対してだけである。ログイン CSRF やクロスサイトのサブリソースリクエストでは要件が異なる場合がある。

**セッション固定と無効化**
ログイン、アカウント切り替え、MFA 完了、なりすまし (impersonation)、その他の権限変更でセッション識別子がローテーションされない、あるいはログアウト、パスワード変更、失効、アカウント無効化の後も有効なままである。サーバーセッション、リフレッシュトークン、署名付き Cookie、WebSocket の状態、キャッシュのコピー、フォールバックのエンドポイントを確認する。

**Cookie のスコープと転送**
機密 Cookie の `Domain` や `Path` が広すぎる、安全でない転送経路を通り得る、あるいは別のコンポーネントが異なる選び方をする兄弟 Cookie と衝突する。フラグの欠如だけであれば、現実的な低信頼のオリジン、ネットワーク上の位置、ブラウザの経路がクレデンシャルを取得または置き換えられない限り、ハードニングの注記にとどめる。

## フェデレーテッドアイデンティティの攻撃クラス (subagent_type: `general`)

まず役割を確定する。リダイレクトの許可リストやコード発行といった認可サーバー側の制御は、リライングパーティーのクライアントの責務ではない。検証と束縛の欠陥は、その成果物を消費するコンポーネントの責務である。

**JWT の検証とクレームの束縛**
署名検証、サーバー側で固定されたアルゴリズムと鍵の取得元を確認し、次に `exp`、`nbf`、`aud`、`iss` を確認する。`kid`、`jku`、`x5u` は信頼できない鍵セレクターとしてレビューし、重複/ヘッダーの正規化、検証なしのデコード経路も見る。別サービス向けの有効なトークンは、信頼された発行者が署名していてもここでは無効である。

**OAuth/OIDC のリクエストとコールバックの束縛**
対象が認可サーバーである場合は `redirect_uri` の所有を厳密に検証する。セッションに束縛された `state`、該当する場合は PKCE と認可コードの束縛、ID トークンの発行者/オーディエンス/署名/nonce、複数プロバイダーのフローでは選択された IdP の束縛を検証する。最初のコールバック、リトライ、モバイル/ディープリンク、アカウントリンクのルートを比較する。

**SAML の署名付きオブジェクトとアサーションの束縛**
署名を検証した要素が、アイデンティティとして使われる要素と同じであることを確かめる。未署名/フォールバックの経路、安全な XML パーサー設定、正規化 (canonicalization) の差異、そして有効期間、オーディエンス/受信者、リクエストの対応付け、リプレイ状態といった鮮度/束縛のフィールドをレビューする。

## MFA、パスキー、アカウント遷移の攻撃クラス (subagent_type: `general`)

**MFA 登録と保証レベルのダウングレード**
登録、置き換え、無効化、リカバリーコード生成、信頼済みデバイスの作成、フォールバックログインには、意図した事前の保証レベルが必要である。有効な第一要素だけで、ポリシーが求める再認証なしに第二要素を登録または置き換えられないこと、無効化された要素や古い要素がセッションを認可しなくなることを確認する。

**ステップアップの束縛と回避**
成功したチャレンジが誤ったセッション、アカウント、テナント、アクション、API リクエストを昇格させる、あるいは別のルートが保証レベルのチェックを省く。チャレンジを、プリンシパル、現在のセッション、目標とする保証レベル、必要な場合は操作やリソース、有効期限、一回限りの完了に束縛する。UI、API、バッチ、回復、再開されたフローの経路を比較する。

**WebAuthn とパスキーの検証**
登録時には、チャレンジ、RP ID、期待するオリジン、クレデンシャル、user/userHandle、アルゴリズム、ポリシーが求めるユーザー検証を、開始したセッションに束縛する。認証時には、チャレンジ、RP/オリジン、クレデンシャルの所属、署名、意図したユーザー存在確認/検証を検証する。アカウント発見とリンクのフローで userHandle やクレデンシャルとアカウントの取り違えがないか確認する。署名カウンターの扱いが意味を持つのは、製品がカウンターの後退をクローンの兆候として扱う場合だけである。

**アカウントリンクとアイデンティティの衝突**
既存アカウントに IdP、パスキー、メール、電話、デバイス、外部アカウントを追加するには、現在の認証済みセッション、新しいアイデンティティの所有の検証、ポリシーが求めるステップアップ、リンクを開始したアカウントに束縛されたコールバック状態が必要である。リンク解除/再リンクと招待受諾の経路で、検証済み識別子やテナントの衝突がないかレビューする。

**パスワードリセットとより広い回復**
回復トークン、サポート/管理者による回復、バックアップコード、デバイス移行、メールや電話の変更は、しばしば最も弱い認証経路になる。トークンのランダム性、ユーザー/アクションへの束縛、有効期限、一回限りの状態、レート/計数の制御、配送 URL の信頼、以前のトークンとセッションの無効化を検証する。公開されたアカウントの存在を明かすだけのレスポンスの差異は、それだけでセキュリティ上の指摘にはならない。

## API キーと mTLS の攻撃クラス (subagent_type: `general`)

**API キーのスコープとリソースの束縛**
キーが、サーバー側のレコードで付与された範囲より広いテナント、リソース、アクション、環境に対して認証される、あるいはリクエストパラメーターがその束縛を上書きする。キーの検索、プレフィックス/シークレット全体の検証、公開可能キーとシークレットキーの型の取り違え、スコープチェック、ローテーション、失効キャッシュ、一括処理のエンドポイントをレビューする。

**API キーの露出と安全でない転送**
キーがクライアントバンドル、URL、リダイレクト、ログ、エラー経路、ビルド成果物、または低信頼のプリンシパルがアクセスできるレスポンスに現れる。キーと呼ばれていても公開識別子はシークレットではない。キーの種類と、漏洩によって得られる権限を確認する。

**mTLS のピアとアプリケーションアイデンティティの取り違え**
プロセスが任意のネットワークピアからのクライアント証明書アイデンティティヘッダーを信頼する、証明書チェーンは検証するが攻撃者が影響を与えられるサブジェクト文字列を誤ってアカウントに対応付ける、あるいは誤った信頼ドメイン、拡張用途、オーディエンス、有効期間ポリシーの証明書を受け入れる。信頼されたプロキシが mTLS を終端する場合は、そのプロキシだけが接続できること、受信したアイデンティティヘッダーをプロキシが除去すること、バックエンドがサニタイズ済みのアイデンティティをリクエストに束縛することを検証する。

**証明書ライフサイクルのフォールバック**
期限切れ、失効、欠落、更新失敗の証明書によって、ベアラーのみや匿名の動作へ暗黙にフォールバックする、あるいは長寿命のプール接続が失効後も認可を保持する。デプロイ側の失効データが見えない場合の結果は `needs_validation` とする。リポジトリ内の fail-open 分岐はソースで確認できる。

## 共通の手順 (上記すべてに適用する)

- すべてのクレデンシャルとチャレンジについて、発行 → 保存 → 送信 → 消費 → 更新 → 失効をたどる。通常、エラー、リトライ、移行、レガシー、アカウント切り替えの経路を比較する。
- 同じアイデンティティへのすべての入口と、同じ機密操作へのすべてのルートを列挙する。実効ポリシーは最も洗練された UI ではなく、並行する経路のうち最も弱いものである。
- パーサー、プロキシ、ルーター、キャッシュ、アプリケーションの正規化を並べて差分を取る。ローカルでの検証では、稼働中のデプロイにトラフィックを送るのではなく、同一の範囲を限ったリクエストフィクスチャを各コンポーネントに与える。
- 回復とリンクについては、アカウントの変更前/変更後のグラフを描く。各辺には、現在のプリンシパル、新しいアイデンティティの証明、必要な保証レベル、コールバック/セッションの束縛、失効の効果を明記する。

## 検証ルール (ここでの指摘を報告する前に必ず適用する)

1. ソースの可視性ゲートを適用する。プロキシチェーン、エッジのキャッシュキー、IdP ポリシー、証明書の信頼、ブラウザの Cookie 挙動、シークレット、デプロイされた認証モードはリポジトリの外にあることがある。見えないインフラの挙動を断定せず、正確な `needs_validation` 候補として記録する。
2. フレーミングとキャッシュの指摘では、両方のコンポーネントと食い違うパース/キーを明記する。リクエスト間、ユーザー間、またはプライベートレスポンスへの影響を、範囲を限ったローカルフィクスチャで確認する。
3. トークン、MFA、パスキー、アカウントリンク、回復、API キー、mTLS の指摘では、検証箇所の行と、欠けているプリンシパル/セッション/リソース/オリジン/オーディエンス/アクション/保証レベルの束縛を引用する。サーバーが不正な遷移やクレデンシャルを受け入れることを証明する。
4. CSRF では、アンビエントクレデンシャル、状態変更ルート、受け入れられるクロスサイトリクエストの形、ブラウザの Cookie ポリシー、欠けている有効なチェックを明記する。読み取り専用のアクションや、アンビエントでないベアラートークンを要するルートは該当しない。
5. フレームワークとライブラリのデフォルトを確認する。バージョンや設定が不明な場合は `needs_validation` とする。未検証の重大な主張を、より低い深刻度の confirmed 指摘にすり替えてはならない。
6. `confirmed` を返すのは、完全なソーストレースと、観測可能な不正なアイデンティティ、状態、または開示がある場合だけである。`needs_validation` では、欠けている事実と、それを解決する安全なローカルまたはオーナー観測のチェックを明記する。
