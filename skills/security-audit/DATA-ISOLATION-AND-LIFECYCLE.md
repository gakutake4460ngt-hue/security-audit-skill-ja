# データ隔離とライフサイクルの調査

#### このファイルを使う場面

対象がマルチテナントまたはアクセス制御されたデータを保存する、検索/インデックス/キャッシュ/分析用のコピーを派生させる、オブジェクトリンクを発行する、レコードをエクスポートまたはリストアする、スキーマをマイグレーションする、あるいは削除、失効、保持の挙動を約束している場合にこのファイルを使う。このドメインは、1 つのデータ項目をすべてのコピーと状態遷移にわたって追跡する。エンドポイント単位のアクセス制御には `ATTACK-CLASSES.md`、プロバイダー単位のストレージポリシーには `CLOUD-AND-DEPLOYMENT.md` を使う。

大きな対象は、プライマリストレージ、キャッシュ/検索、オブジェクト/Blob ストレージ、分析/ログ、エクスポート/バックアップ、削除/失効、マイグレーションごとに分割する。

## 基本原則 (このドメインのすべてのエージェントプロンプトに含める)

```
- A tenant or owner field on a record is not isolation. Find the query, key, path, policy, or row-level control that enforces it for each read and write path.
- Trace derived copies. Sanitized primary data can become unsafe in search, cache, analytics, export, previews, logs, replicas, and backups with different ACL and retention rules.
- Deletion and revocation are lifecycle contracts. Check current, historical, cached, indexed, exported, restored, and queued copies within the product's stated boundary.
- Privacy or retention preference is not automatically a security vulnerability. Require an explicit data-access boundary or deletion/revocation guarantee and an unauthorized reader or later operation.
- Use `confirmed` for complete source-visible lineage and bounded dummy-tenant tests. Use `needs_validation` when external storage policy, retention, CDN behavior, replica lag, or backup access is unavailable.
```

## テナントとオブジェクトの隔離の攻撃クラス (subagent_type: `general`)

**テナントまたはオーナーの強制の欠如**
読み取り、更新、削除、一覧、件数取得、一括クエリが、認証されたテナント/オーナーに束縛せずにオブジェクトを特定する、あるいはそのアイデンティティをリクエスト本体のフィールドに委ねて信頼する。直接の検索、ネストしたリレーション、バックグラウンド、管理者、インポート、レガシーの経路を比較する。

**複合キーと名前空間の衝突**
キャッシュキー、オブジェクトパス、データベースの一意性、検索ドキュメントの ID、一時ファイル、重複排除キーにテナントや環境が含まれない。アプリケーションのレコードは別々のオーナーを持っていても、2 つのプリンシパルが同じ論理キーを上書きまたは取得できる。

**ポリシーとクエリの不一致**
行レベルのポリシー、ORM のデフォルトスコープ、認可フィルター、生の/バイパス用クライアントが異なる述語を適用する。結合、集計、エイリアス、ビュー、トランザクション、`unscoped` やサービス用クライアント、コンテキストが欠けているエラー経路を確認する。

**Blob と署名付き参照の越権**
オブジェクトキー、添付ファイル ID、バージョン ID、共有リンク、署名付き URL が、発行したプリンシパルのアクセス範囲を超える操作や名前空間を許す、あるいは元の ACL が変更された後も有効なままである。操作、正確なオブジェクト/バージョン、オーディエンス、有効期限、テナントを束縛する。

## 派生データと情報開示の攻撃クラス (subagent_type: `general`)

**検索、キャッシュ、インデックスの ACL ドリフト**
プライマリレコードの ACL やライフサイクルが変わっても、検索可能なコピー、キャッシュ、埋め込み、サムネイル、RSS、プレビュー、インデックスのコピーが無効化されない。ドキュメントの取り込みと無効化だけでなく、取得時のフィルタリングも検証する。

**別の読み手としての分析、ログ、トレース、診断**
プライベートなコンテンツやクレデンシャルが、より広いアクセス、より長い保持期間、テナントの混在を持つシステムに出力される。データの分類と現実的な読み手を確認する。フィールド名、公開識別子、意図したポリシー下でのオペレーター専用のコンテンツだけでは不十分である。

**列挙と集計によるオラクル**
件数、フィルター、並び順、エラー、一意制約、タイミング、通知の挙動、存在チェックが、保護されたオブジェクトやアカウントの状態を明かす。一般的なレスポンスの差異ではなく、具体的な機密の述語と観測可能な区別を要件とする。

## エクスポート、バックアップ、リストア、マイグレーションの攻撃クラス (subagent_type: `general`)

**エクスポートとバックアップのスコープの拡大**
エクスポート、スナップショット、ポータビリティパッケージ、レポート、バックアップに、他のテナント、アクセスできないオブジェクトのフィールド、論理削除されたデータ、シークレットの値、要求者のアクセス範囲を超える履歴が含まれる。選択後の項目ごとの認可と、最終成果物をダウンロードする認可を確認する。

**インポートとリストアによる権限の拡大**
リストア/インポートが、オーナー、スキーマ、ACL、一意性、検証のルールを迂回する、既存のリソースを上書きする、あるいは要求者が書き込めないテナントにレコードを再作成する。アーカイブの中身を信頼できないものとして検証し、以前の出所を信頼するのではなく結果として生じる操作を認可する。

**マイグレーションのデフォルトと所有権の取り違え**
古いレコードにテナント/ACL/ライフサイクルのフィールドがない、互換性のない ID が衝突する、あるいは段階的なロールアウトによって新旧の読み手が異なるデフォルトを適用する。バックフィル、二重読み書き、互換性、ロールバック、再開されたマイグレーションの経路をレビューする。

**バックアップとレプリケーションの境界のドリフト**
暗号鍵、ストレージアカウント、クロスリージョンのレプリカ、リストア環境、サポート用のスナップショットが、プライマリデータより広いアイデンティティやテナントのスコープを持つ。ソースで確認できるのはリポジトリ内のポリシーだけである。ホストされた環境のアクセスと保持には `needs_validation` が必要である。

## 削除、失効、ライフサイクルの攻撃クラス (subagent_type: `general`)

**論理削除とトゥームストーンの回避**
直接の検索、検索、リレーションのたどり、オブジェクトリンク、バックグラウンド処理、リストアがライフサイクルの述語を無視し、削除/失効済みのレコードを返す、またはそれに対して操作する。すべての参照が消える前に、論理削除された識別子を再登録できるかを確認する。

**古い認可と派生コピーの使用**
メンバーシップの削除、ACL の更新、同意の撤回、シークレットの失効、ロールの降格が、将来の操作を引き続き認可するセッション、キャッシュ、サブスクリプション、ジョブ、マテリアライズされたデータを無効化しない。

**保持期間とキュー投入済みの作業の超過**
プライマリストレージでは削除が完了しても、キュー上の処理、リトライ、エクスポート、分析、生成された成果物が、約束された境界を超えてデータを再作成または保持する。冪等な削除とトゥームストーンの伝播を探す。

**リストアによる不正な状態の再導入**
バックアップ、取り消し、削除の取り消し、レプリカからの回復が、現在のポリシーではもはや許されないデータ、クレデンシャル、メンバーシップ、パーミッションを復元する。復元された状態を再認可し、スナップショット後に行われたライフサイクルの変更を再適用する。

## 共通の手順 (上記すべてに適用する)

- 保護されたレコードを 1 つ選び、プライマリへの書き込み、クエリ、キャッシュ、インデックス、イベント、エクスポート、バックアップ、削除、リストアの経路を描く。各辺にプリンシパルとテナントを記す。
- 2 つのダミーテナントを同じローカルのサービスメソッドで比較し、ACL の変更、削除、アカウント切り替え、リストアの後に繰り返す。実際のユーザーデータは使わない。
- バイパス用クライアント、バックグラウンドジョブ、マイグレーション、グローバルな一意性、キャッシュキーから始める。これらの経路は、対話型のエンドポイントが持つリクエストスコープのアイデンティティを省きがちである。

## 検証ルール (ここでの指摘を報告する前に必ず適用する)

1. 攻撃者またはより低信頼のプリンシパル、保護されたデータ/状態、影響を受けるオーナー/テナント、別のコピーまたは操作、不正な情報開示または変更を明記する。
2. 意図した信頼できる情報源 (source of truth) のポリシーと、それを省く、または食い違う経路の両方を引用する。別の層が同じテナント/ライフサイクルの条件を強制していないことを確認する。
3. ローカルのダミーテナントと機密でないフィクスチャを使って、スコープを越えたアクセスや古いライフサイクルの挙動を証明する。観測可能な最小限のレコードまたは操作で止める。
4. 外部のキャッシュ、オブジェクトストレージ、レプリカ、分析、バックアップ、保持のポリシーが必要な場合は `needs_validation` に分類し、オーナー観測のチェックを明記する。
5. `confirmed` を返すのは、完全な系譜 (lineage) と具体的な境界への影響がある場合だけである。`needs_validation` は、未解決の正確なストレージ、ACL、無効化、保持、リストアの事実とともに返す。
