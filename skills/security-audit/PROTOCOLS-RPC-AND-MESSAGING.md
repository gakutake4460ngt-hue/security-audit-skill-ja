# プロトコル・RPC・メッセージングのハンティング

#### このファイルを使う場面

対象が、gRPC、GraphQL のトランスポート、Cap'n Proto、Thrift、Protobuf、独自バイナリプロトコル、ストリーミング RPC、Webhook、ブローカー、キュー、pub/sub、イベントバスを使う場合にこのファイルを使う。ピア ID、メッセージの論理的な解釈、ルーティング、リプレイ、順序、配信セマンティクスを扱う。パーサーのメモリ安全性には `MEMORY-SAFETY-AND-BINARY.md` を、HTTP のフレーミングには `WEB-PROTOCOL-AND-AUTH.md` を、可用性への影響には `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` を使う。

大きなシステムは、プロデューサー/コンシューマーの組、外部/内部のピアの役割、同期 RPC、ストリーミング、非同期メッセージ経路ごとに分割する。

## 基本規律 (この領域のすべてのエージェントプロンプトに含める)

```
- "Internal" is not authentication. Name the peer identity at every hop and show how it becomes the application principal used for authorization.
- Schema validation proves message shape, not provenance, resource authority, ordering, or safe values. Follow decoded fields to policy and side effects.
- Broker guarantees and application guarantees differ. Write down retry, ordering, acknowledgement, deduplication, and transaction behavior before evaluating state changes.
- Parser disagreement requires two concrete consumers, schema versions, or wire representations and one security-relevant divergent value.
- Use `confirmed` for source-complete paths plus bounded local producer/consumer tests. Use `needs_validation` for broker ACL, service-mesh identity, topic attachment, or compatibility behavior outside the repository.
```

## フレーミング・スキーマ・解釈の攻撃クラス (subagent_type: `general`)

**メッセージ境界と正規化の不一致**
コンポーネント間で、長さ、圧縮、重複フィールド、未知のフィールド、エンコーディング、数値の幅、正規化、エンベロープと本文の優先順位についての解釈が食い違う。生成されたパーサーと独自パーサー、ゲートウェイ、言語バインディング、バージョン変換器を比較する。デコード後にどのプリンシパル、リソース、操作が異なるかを確認する。

**union・enum・デフォルトの混同**
未知のバリアント、欠落した判別子、ゼロ値、デフォルトの権限、互換性マッピングが、検証済みのケースを前提とするコードに到達する。網羅的なディスパッチ、デフォルト分岐、古いコンシューマーが新しく追加されたフィールドをどう解釈するかをレビューする。

**エンベロープとペイロードの ID 不一致**
認可は信頼できそうなルーティング情報やエンベロープのメタデータを使う一方、ハンドラは本文中の矛盾するテナント、アカウント、サブジェクト、オブジェクト、送信者に基づいて動作する。どのソースが権威を持つかを特定し、クライアントがそれを上書きできないことを確かめる。

## RPC の ID と認可の攻撃クラス (subagent_type: `general`)

**インターセプターとメソッドパスの不整合**
認証/認可のインターセプターが unary メソッドには適用されるが、ストリーム、リフレクション、ヘルスチェック、ゲートウェイでトランスコードされたパス、互換性サービス、個々のストリームメッセージには適用されない。同じ操作に至るすべての登録とルートを比較する。

**ピア ID とアプリケーションプリンシパルの混同**
mTLS、ワークロード ID、bearer メタデータ、転送された ID、ブローカーのクレデンシャルがチャネルを認証するが、呼び出し側が制御するフィールドがユーザーやテナントを選択する。チャネルの ID と主張されたプリンシパルは、決定論的なポリシーで束縛されていなければならない。

**アイテム単位・ストリーミングの認可の欠落**
ストリーム、サブスクリプション、バッチ、一括メッセージが一度だけ認可され、その後のアイテムが別のリソースを指定する、あるいはロール、メンバーシップ、トークンの失効後も続行する。スコープが変わりうる箇所で再確認し、サブスクリプションを元のプリンシパルに束縛する。

**コールバックと応答の対応付けの混同**
予測可能な、再利用される、またはテナントをまたぐ相関 ID により、応答、Webhook、キャンセル、確認応答が別の呼び出し元の保留中操作を満たしてしまう。未完了の各リクエストを、認証済みピア、テナント、操作、ライフサイクルに束縛する。

## ブローカーとキューの分離の攻撃クラス (subagent_type: `general`)

**トピック・ルーティングキー・サブスクリプションのスコープの欠落**
パブリッシャーやサブスクライバーが、別テナントのトピック、ワイルドカード、コンシューマーグループ、パーティション、応答キュー、デッドレターのルートを選択できる。見える範囲でブローカーが強制する ACL と、アプリケーション側での名前空間の構築を確認する。ペイロード内のテナント文字列は分離ではない。

**デッドレター・リトライ・診断情報からの開示**
デッドレターキュー、エラートピック、トレース、オペレーター向けビューに送られたメッセージが、信頼度の低いコンシューマーからアクセス可能な秘密情報やテナントをまたぐペイロードを含む。通常の配信だけでなく、失敗経路でのポリシーと秘匿化をレビューする。

**コントロールプレーンとして扱われる信頼できないプロデューサー**
メッセージ本文が、独立に認証されたプロデューサーとイベント種別なしに、自身を管理イベント、プロバイダーのコールバック、レプリケーションレコード、マイグレーション指示であると宣言できる。特権的な処理の前に、署名と、ソース/アカウント/audience への束縛を検証する。

## リプレイ・順序・トランザクションの攻撃クラス (subagent_type: `general`)

**重複配信と冪等性の欠落**
重複排除がない、変更後に行われる、またはテナントや操作をまたいで衝突するキーを使うため、リトライや再配信が副作用を繰り返す。ブローカーの配信モデルと、本来冪等ではない副作用を確認する。

**順序の乱れた・古いメッセージの受け入れ**
古い状態、失効したメンバーシップ、キャンセルされた処理、ステップアップ前の認可が、新しい状態の後に届いてそれを上書きする。シーケンス/バージョンのチェック、トゥームストーン、パーティションの変更、リストア/リプレイのワークフローをレビューする。

**確認応答/コミットの順序の欠陥**
確認応答が永続的なコミットより前に行われてセキュリティ上重要な処理が失われる、あるいはコミットが信頼性の低い確認応答より前に行われて変更が重複する。トランザクショナル outbox/inbox の挙動と障害復旧を評価する。

**複数コンシューマーにまたがる部分的な遷移**
複数のコンシューマーが共同で 1 つの認可またはビジネス上の遷移を実装しているが、リトライや部分的な失敗により一部だけがコミットされる。アトミックに永続化すべき不変条件、または現在の認可で補償すべき不変条件を特定する。

## 共通の手順 (上記すべてに適用)

- メッセージファミリーごとに、プロデューサー → ブローカー/トランスポート → ゲートウェイ → コンシューマー → ストレージを描く。各ホップで、認証済みピア、権威を持つテナント/リソースのフィールド、検証、副作用を記録する。
- 同じ小さなフィクスチャを、リポジトリ内のすべてのスキーマバージョンや言語バインディングに入力する。負荷を発生させずに、重複、欠落、未知、境界値、リプレイ、順序入れ替えのメッセージをテストする。
- 通常、リトライ、デッドレター、リプレイ、マイグレーション、リフレクション、ストリーム、ゲートウェイでトランスコードされたルートを比較する。セキュリティポリシーはトランスポートの変化を経ても維持されなければならない。

## 検証ルール (ここでの指摘を報告する前に必ず適用)

1. 現実的なプロデューサーまたはピア、受け入れられたメッセージ、認証済みチャネルの ID、影響を受けるプリンシパル/リソース、認可されていない変更または開示を示す。
2. 不一致の主張では、両方のパーサー/コンシューマーと、食い違うデコード値を示す。どちらかの側が安全に拒否する場合は確定できない。
3. リプレイ/順序の主張では、実際の配信保証を確定し、範囲を限ったローカル/インメモリのトランスポートで不変条件の破綻を再現する。
4. 認可と分離では、ソースから見えるインターセプター、ブローカー ACL、ゲートウェイ、コンシューマーのすべての層を検証する。外部での接続設定に依存する場合、候補は `needs_validation` とする。
5. `confirmed` は、メッセージのライフサイクル全体と観測された意味のある結果がある場合にのみ返す。必要なブローカー、サービス ID、ルート、配信に関する事実を正確に添えて `needs_validation` を返す。
