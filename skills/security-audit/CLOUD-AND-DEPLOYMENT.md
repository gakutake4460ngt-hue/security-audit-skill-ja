# クラウドとデプロイの調査

#### このファイルを使う場面

リポジトリがクラウドのアイデンティティ、インフラストラクチャ、コンテナ、Kubernetes、サービスメッシュ、サーバーレス関数、エッジワーカー、イングレス、オブジェクトストレージ、マネージドサービス、環境ごとの設定を定義している場合にこのファイルを使う。このドメインは、デプロイされたコンポーネントが意図したアイデンティティ、隔離、ネットワーク到達性、シークレット、ポリシーを受け取っているかを問う。ソースは稼働中の事実ではなく意図を表していることが多いので、ソースで確認できた欠陥とデプロイ環境での検証が必要なものを区別する。

ビルドと昇格 (promotion) の信頼には `SUPPLY-CHAIN-AND-RELEASE.md`、HTTP プロキシのセマンティクスには `WEB-PROTOCOL-AND-AUTH.md`、データストアのテナントスコープには `DATA-ISOLATION-AND-LIFECYCLE.md` を使う。

## 基本原則 (このドメインのすべてのエージェントプロンプトに含める)

```
- Do not infer a live exposure from a manifest alone. Establish which environment consumes it, what defaults or overlays modify it, and whether the source path is active.
- Map each workload's identity to specific operations and resources. Broad policy is a finding only when lower-trust input can reach an unauthorized action.
- Ingress, proxies, service mesh, metadata services, and admission policy are real boundaries, but only count a control when its configuration and attachment are visible.
- Secret references are not secret disclosure. Require a lower-trust reader, output, artifact, log path, or unsafe fallback.
- Use `confirmed` for active in-repo configurations and local rendering/policy validation. Use `needs_validation` for account policy, network attachment, runtime admission, hosted metadata, or drift that needs owner observation.
```

## ワークロードアイデンティティと IAM の攻撃クラス (subagent_type: `general`)

**ワークロードアイデンティティの越権**
ワークロード、Pod、関数、エッジワーカー、ノードのアイデンティティが、その役割を超えるテナント、アカウント、リソース、API に対して操作でき、信頼できないリクエストやジョブの入力がその対象を選択する。クラウドポリシーの条件、リソースパターン、サービスアカウントの割り当て、名前空間の対応付け、フォールバックのクレデンシャルをレビューする。

**クロスアカウントまたはクロステナントのロールの取り違え**
ロールの引き受け (assume role)、外部 ID、トークン交換、ワークロードフェデレーション、リソースポリシーが、意図した送信元アカウント、オーディエンス、リポジトリ、名前空間、ワークロードに束縛されていないアイデンティティクレームを受け入れる。信頼ポリシーと、呼び出し元が制御するクレームの両方を確定する。

**クラウドメタデータに委ねられたアプリケーション認可**
アプリが、呼び出し元が供給したアイデンティティヘッダー、タグ、ラベル、アカウント ID、リソースメタデータを、それがクラウドのコントロールプレーンや信頼されたプロキシから来たことを検証せずに信頼する。クラウド IAM とアプリケーションの認可は別個のチェックである。

## イングレス、ネットワーク、コントロールプレーンの攻撃クラス (subagent_type: `general`)

**予期しないサービスまたは管理プレーンへの到達性**
イングレス、サービス、リスナー、セキュリティグループ、ロードバランサーのアノテーション、ポートマッピング、サーバーのバインドが、管理、デバッグ、メトリクス、ノード、コントロールプレーン、内部の API を、より低信頼のネットワークに公開する。ネットワーク制御が欠けているだけなら `needs_validation` である。リポジトリで制御される公開ルートが機密ハンドラーに通じている場合は `confirmed` になり得る。

**信頼されたプロキシとメッシュのアイデンティティの回避**
バックエンドが、意図したイングレス/サイドカーの外にあるピアから、転送されたアイデンティティ、mTLS のサブジェクト、認可メタデータを受け入れる、あるいは別のポートやヘルスチェック/レガシーのパスがメッシュを迂回する。ヘッダーの除去、ピアの到達性、プロキシが存在しない場合の fail-open の挙動を検証する。

**メタデータと内部サービスへの到達性**
信頼できない URL、宛先、プロトコルの選択が、ワークロードのクレデンシャルを伴ってインスタンス/コンテナのメタデータ、コントロールプレーンのソケット、内部 API に到達する。URL のパースとリダイレクトの処理は `ATTACK-CLASSES.md` に従ってたどる。ここでは、デプロイされたネットワーク、メタデータのバージョン、アイデンティティの境界を確定する。

## コンテナとオーケストレーションの攻撃クラス (subagent_type: `general`)

**ホストまたはコントロールプレーンの能力の露出**
より低信頼のワークロードが、特権モード、ケーパビリティ、ホストの名前空間、ホストパス、デバイスのマウント、コンテナランタイムのソケット、サービスアカウントトークンを選択でき、それがノード/コントロールプレーンの権限にまで及ぶ。seccomp や読み取り専用ファイルシステムが単に欠けているだけなら、到達可能な操作がその境界を越えない限りハードニングの扱いである。

**アドミッションとポリシーの経路の不一致**
あるデプロイ経路はイメージのアイデンティティ、名前空間、リソース、シークレット、特権のポリシーを強制するが、別のコントローラー、ジョブ、アップグレード、リストア、互換性の経路は強制しない。その別経路と、結果としてデプロイされるオブジェクトを確認する。

**名前空間とラベルの信頼の取り違え**
ネットワーク、アドミッション、シークレット、ワークロードアイデンティティのポリシーが、より信頼の低いプリンシパルが設定できるラベル、アノテーション、名前、名前空間に依存している。誰がセレクターを制御できるかと、一致したときにどんな権限が与えられるかを比較する。

## 設定とシークレットのライフサイクルの攻撃クラス (subagent_type: `general`)

**セキュリティ制御の優先順位のドリフト**
開発用の値、チャートのデフォルト、環境変数、コマンドラインフラグ、フィーチャーゲート、サイドカーの注入、リージョンごとのオーバーレイが、デプロイされた環境で認証、転送の安全性、テナントのスコープ、監査ポリシーを無効にする。ベースのファイルだけでなく、保守されている各デプロイについて最終的な設定をレンダリングする。

**ワークロード境界を越えたシークレットの露出**
シークレットが、別のワークロードやテナントからアクセスできるログ、クラッシュレポート、プロセス引数、共有された環境、広範なボリューム、ビルド出力、サービスディスカバリー、読み取り API に入る。シークレットの種類と権限を確認する。公開エンドポイントや鍵 ID はクレデンシャルではない。

**クレデンシャルの更新と障害時のフォールバック**
ワークロードのクレデンシャルのマウント、更新、ローテーション、失効に失敗した結果、古いクレデンシャルが有効なまま残る、あるいはアプリがより信頼の低いアイデンティティモードを受け入れる。起動時、レディネス、再接続、キャッシュされたクライアントの挙動をレビューする。

## マネージドストレージ、イベント、エッジの攻撃クラス (subagent_type: `general`)

**オブジェクトと署名付き URL のポリシーの取り違え**
バケット/コンテナのポリシー、オブジェクトキー、CDN のオリジン、署名付き URL が、プリンシパル、操作、オブジェクトの名前空間、オーディエンス、有効期限を束縛していない。読み取りだけでなく、一覧/バージョンの操作と書き込みの経路もレビューする。

**イベントソースのアイデンティティの取り違え**
関数やワーカーが、プロバイダーが署名したエンベロープ、サブスクリプション/トピック、アカウント、リージョン、リプレイ状態を検証せずに、イベント本体のフィールドを送信元のアイデンティティとして信頼する。プッシュ、プル、リトライ、デッドレターの経路を比較する。

**エッジ/ランタイムの境界の不一致**
エッジやサーバーレスのランタイムが、オリジンのランタイムとは異なるシークレット、API、ファイルシステム、隔離、テナントポリシーを前提にしており、オリジンへのフォールバックによって権限やキャッシュの挙動が変わる。どの設定が各経路を選択するかを確認する。

## 共通の手順 (上記すべてに適用する)

- 保守されているすべての環境をレンダリングし、外部ポート、ワークロードアイデンティティ、ネットワークのピア、マウントされたシークレット、クラウドリソースのマトリクスを作る。差異にはオーナーまたはポリシーによる説明が必要である。
- より低信頼のリクエスト、オブジェクト、ラベル、イベントをクラウドポリシーまで追う。どのワークロードのクレデンシャルが最終的な操作を実行し、どの条件がそれをスコープすべきかを示す。
- 通常のデプロイ、マイグレーション、リストア、ノードのメンテナンス、フェイルオーバー、ローカル/エミュレーターの経路の差分を取る。メッシュ、アドミッション、アイデンティティ、シークレット、ポリシーのサービスが利用できないときの挙動をレビューする。

## 検証ルール (ここでの指摘を報告する前に必ず適用する)

1. 有効なソース経路と実効的なデプロイオブジェクトを確定する。できない場合は `needs_validation` とし、どのレンダリング済みマニフェストまたはオーナー観測の割り当て情報が欠けているかを明記する。
2. より低信頼の呼び出し元/ワークロード、クラウドまたはアプリケーションのアイデンティティ、制御可能なセレクター、影響を受けるリソース、不正な操作または情報開示を明記する。
3. 固定されたバージョンでのプロバイダーとオーケストレーターのデフォルトを確認する。パブリック IP、到達可能なメタデータサービス、緩いファイアウォール、アドミッションの未割り当てを仮定しない。
4. ローカルでの検証では、テンプレートのレンダリング、ポリシーの評価、隔離されたフィクスチャ内でのコンテナ/ユーザー名前空間の調査、ダミーのアイデンティティを使ったエミュレーターの実行を行ってよい。稼働中のエンドポイントを探査したり、共有されたクラウドリソースを変更したりしない。
5. `confirmed` を返すのは、有効なソースの完全なトレースと具体的な境界の結果がある場合だけである。`needs_validation` は、必要となる正確なデプロイ済みポリシー、アイデンティティの割り当て、オーバーレイ、ネットワーク、ドリフトの観測とともに返す。
