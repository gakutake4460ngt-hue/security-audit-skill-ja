# リソース枯渇と可用性のハンティング

#### このファイルを使う場面

信頼できないリクエスト、メッセージ、ファイル、テナント状態、エージェントの処理が、CPU、メモリ、ディスク、接続、ワーカースロット、有料 API、キュー容量を消費しうる場合、または共有サービスをデッドロック/クラッシュさせうる場合にこのファイルを使う。この領域では、ソースレビューで確認できる可用性の脆弱性と一般的な性能問題を区別する。共有サービスや稼働中のサービスに負荷をかけて検証してはならない。

メモリ完全性の欠陥には `MEMORY-SAFETY-AND-BINARY.md` を、ブローカーの配信ロジックには `PROTOCOLS-RPC-AND-MESSAGING.md` を使う。到達可能な致命的エラーは、基盤となるパーサーが別のファイルで扱われていても、共有への影響の観点からここに属する。

## 基本規律 (この領域のすべてのエージェントプロンプトに含める)

```
- Require an input-to-cost path, a missing effective bound, and impact on another user, shared service, safety function, or operator-owned spend. Self-limiting work in the requester's own process is not a service vulnerability.
- A missing rate limit is not enough. Check body/message/file caps, concurrency, queues, deadlines, database constraints, upstream gateways, and per-tenant quotas before calling a path unbounded.
- Do not run stress, saturation, or production tests. Use asymptotic analysis, small boundary fixtures, mocked paid calls, strict local resource limits, and deterministic cancellation tests.
- State attacker cost, service work, persistence, scope, and recovery. One bounded input with superlinear or persistent shared effect is materially different from sustained volume.
- Use `confirmed` for source-visible bounds failures demonstrated safely. Use `needs_validation` when upstream caps, deployed topology, autoscaling, paid quota, or recovery behavior is outside the repository.
```

## 計算量増幅の攻撃クラス (subagent_type: `general`)

**超線形なパース・マッチング・評価**
受け入れられる小さな入力が、正規表現の壊滅的なバックトラッキング、ネストしたパース、再帰的な検証、記号的評価、グラフ探索、テンプレート展開、敵対的なソート/ハッシュの挙動を引き起こす。受け入れられる深さ/要素数と計算量を導き、上限を設けた増加曲線をローカルで示す。

**展開と表現による増幅**
圧縮された、疎な、ネストした、エイリアスを持つ、またはエンコードされた入力が、チェックされた転送サイズやファイルサイズをはるかに超えて展開される。アーカイブ、画像、フォント、構造化ドキュメント、プロトコルの圧縮テーブルを含め、各展開の後とパーサーの各段階をまたいで上限を検証する。

**データベースと下流クエリの増幅**
クエリの深さ、フィルタの要素数、ページネーション、展開フィールドに上限がないため、小さなリクエストが、広範なスキャン、病的な結合、ファンアウト、際限のないソート/集計、多数の下流呼び出しを生む。認可が同じリソース範囲を意図的に許可していないことを確認する。

## リソース蓄積の攻撃クラス (subagent_type: `general`)

**際限のないバッファリングと要素数**
本文、順序の乱れたストリーム、アップロード、セッション、一意なキャッシュキー、メトリクスのラベル、ログのフィールド、サブスクリプション、保留中のジョブが、アイテム単位と全体の上限なしに蓄積する。切断、タイムアウト、キャンセル、部分的なパースの際の掃除と期限切れ処理を見つける。

**ファイルディスクリプタ・ハンドル・一時リソースのリーク**
不正な処理やキャンセルされた処理が掃除を漏らし、ソケット、ファイル、データベースカーソル、タイマー、サブプロセス、一時ファイル、オブジェクト参照を保持し続ける。上限を設けたローカルの反復でリークが繰り返され、共有プールに影響することを確認する。

**キャンセル後に切り離された処理**
クライアントのタイムアウト、切断、キャンセルされたジョブ、失敗した認可で制御は戻るが、データベース、モデル、ネットワーク、ワーカーの処理が動き続ける。キャンセルとデッドラインの伝播をすべての層で追跡する。

## クォータとスケジューリングの攻撃クラス (subagent_type: `general`)

**認証前の処理の不均衡**
高コストなパース、鍵の検索、暗号処理、展開、外部リクエストが、認証と最初のサイズ/レートのゲートより前に行われる。リクエスト元の最小限の労力と共有サービスのコストを比較し、上流の制限を確認する。

**クォータ計算のスコープとリセットの欠落**
計算が、攻撃者が影響できる IP、ルート、テナント、キーのプレフィックス、タスク ID などの次元を使うため、あるプリンシパルの処理が意図した予算から逃れたり、別のプリンシパルの割り当てを消費したりできる。整数オーバーフロー、分散環境での競合、リトライ、再接続、アカウント切り替えをレビューする。

**ワーカー・プール・優先度の飢餓**
低優先度または攻撃者が制御するジョブが、無関係なユーザーに必要な共有ロック、ワーカー、データベースプール、イベントループのターン、スケジューラの優先度を占有する。キュー/並行性の公平性を回避する経路、またはデッドラインを超えてスロットを保持する経路を要件とする。

## 障害と復旧の攻撃クラス (subagent_type: `general`)

**到達可能な致命的エラーやデッドロック**
信頼できない入力が、共有プロセス内の `panic`、abort、致命的なアサーション、未処理の例外、プロセス終了、ロックの循環、無限ループに到達する。スーパーバイザーの範囲と、1 つのワーカーだけかサービス全体が利用不能になるかを確認する。分離されたワーカーが再起動されれば影響は減りうるが、欠陥が消えるわけではない。

**リトライストームとフェイルオープンの増幅**
タイムアウト、依存先のエラー、部分的に処理されたメッセージ、ヘルスチェックの失敗が、ジッター、上限、サーキットブレーカー、重複排除なしに、同期した、または際限のないリトライを引き起こす。上限のある 1 つの障害源が、持続的な全体の処理量を生み出せることを検証する。

**ポイズンレコードと head-of-line ブロッキング**
1 つの不正なレコードやメッセージが、共有キュー、パーティション、起動時スキャン、マイグレーション、復旧ループの先頭で繰り返し失敗する。スキップ/隔離のポリシー、オフセット、ブロックされた単位を他のテナントが共有しているかをレビューする。

**安全でない復旧とキャパシティのロールバック**
再起動、リストア、フォールバック、掃除の経路が、際限のない状態を再構築する、現在のクォータを無視する、または直ちに障害を繰り返す入力を復元する。復旧の正しさは可用性の一部である。

## 共通の手順 (上記すべてに適用)

- 入力とリソースの対応表を作る。最初に受け入れられるサイズ/要素数、認証前の処理、下流のファンアウト、永続化、共有プール、上限と掃除の担当、復旧である。
- 全体の上限とオブジェクト単位の上限を比較する。有効な 1 バイトのアイテム 1 万個は、メッセージ単位の上限を回避しつつ、テナント全体やプロセス全体の状態を枯渇させうる。
- 厳格な CPU/メモリ/時間の制限と小さな増加点を持つ、分離されたフィクスチャでのみ検証する。外部呼び出しと有料呼び出しはモックし、上限やキャンセルの欠如が観測できた時点で止める。

## 検証ルール (ここでの指摘を報告する前に必ず適用)

1. 信頼できない入力、リクエスト元の処理量、サービス側の増幅または保持されるリソース、共有への影響範囲、復旧を示す。具体的な共有への影響がない上限の欠如はハードニングである。
2. ソースから見える上流、パーサー、キュー、テナント、フレームワークの上限がその経路を防いでいないことを確認する。デプロイ済みの制御が不明な場合は `needs_validation` とする。
3. 超線形な挙動では、受け入れられる計算量と上限を設けたローカルでの増加を確定する。リークでは、掃除が行われるべき後に保持が繰り返されることを示す。致命的な経路では、プロセス/スーパーバイザーの分離を特定する。
4. リクエスト元の処理量の少なさ、認証なしでの到達可能性、テナントをまたぐ範囲、永続性、復旧の悪さで優先度を付ける。可用性に影響を与える形で検証しない。
5. `confirmed` は、安全なローカルでの証明と意味のある共有への影響がある場合にのみ返す。オーナーが確認すべき上流の制限、トポロジー、クォータ、復旧の観測を正確に添えて `needs_validation` を返す。
